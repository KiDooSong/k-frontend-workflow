# scoped work 소비자 pilot — E2 baseline 과 E3 채택 뒤 재측정

#248 의 E2(baseline)와 E3(채택 뒤 재측정) 결과를 공개 가능한 수준으로 요약한다. 원문·증거는 pilot 소비자 저장소에 비공개로 있다.

- **E2.** 채택 없이 현행 방식으로 대표 작업 4개를 새 에이전트에게 다시 맡겨 기록했다.
- **E3.** 같은 시작 커밋에 킷 `17b5a09` 와 pilot 화면의 scoped 채택을 얹고, 같은 지시문으로 다시 맡겼다.
- **해석.** 측정 결과의 해석과 확대 여부는 사람 결정이다(#248 「사람 결정 항목」). 이 문서는 관찰한 사실만 적는다.

## 킷 관찰 (사실)

1. **binding basis 가 owner projection 전체다.**
   - 사례 3 의 reconcile 편집 하나가 각각 단독으로 pilot 화면의 binding 23건을 모두 stale(`conservative-default`)로 만들었다. 편집은 Unknown 근거 문장 수정, 결정 1행 추가, 충돌 1행 추가였다.
   - scoped 거부는 3건에서 53건이 됐다.
   - 코드: `scripts/lib/scoped-work-basis.mjs` 의 `scopedBindingBasis` 는 projection 전체에 binding 을 더해 해시한다.
2. **v2 Items 대상 문법과 화면 접두 local ID.**
   - `scripts/lib/reconciliation-items.mjs` 의 `parseTargetRef`(`CHILD_KIND_PREFIX`)는 decision·unknown ID 가 `D-`·`U-` 로 시작해야 한다.
   - pilot 은 `<SCREEN>-D###`·`<SCREEN>-U###` 꼴이다. 그래서 `structured_since` 뒤에 캡처하는 사용자 노트 입력을 만들 수 없었다.
   - scoped 판정은 같은 ID 를 받는다.
3. **scoped 판정은 커밋된 HEAD 를 baseline 으로 읽는다.** 의도된 성질이다(커밋하지 않은 편집은 baseline 권한을 바꾸지 못한다). 편집별 가정 실험에는 임시 커밋이 필요했고, 에이전트가 그 커밋에 훅 우회를 썼다.
4. **채택 owner 의 파일 삭제를 여는 authority 가 없다.** scoped request 는 `change` A/M 만 받는다(exit 2). current 는 `CW-WORK-SELECTION-REQUIRED` 로 거부한다.
5. **채택 owner 경로는 current 작업에서 빠진다.** 사례 2 의 주석 정합 6파일 가운데 4파일이 채택 owner 경로였다. scoped unit 이 막힌 동안에는 손댈 수 없었다.
6. **unit 계약 목록은 명시 열거다.** reconcile 이 매핑 행을 늘리면, 사람이 unit 선언을 갱신해야 새 행이 unit 에 들어간다.
7. **`approval_ref` 대상은 도구가 검증하지 않는다.** 이번 측정은 사전 등록 조건을 숨기려고 대상 문서를 측정 트리 밖에 두었다. 네 사례 모두 이 부재를 보고했다.
8. **판정 비용.** scoped `readiness --work` 1회가 90–151초였다. 시작 상태를 만들 때 binding digest 계산은 시작점당 약 11분이었다.
9. **auto mode 분류기.** 사례 1 에서 scoped 요청 파일 작성이 거부됐다. E2 사례 1 은 current `--work` 실행이 거부됐다. 사례 2·3·4 는 같은 형태의 요청 파일과 판정이 거부되지 않았다.

## D 부분 판정(W21·W23·W27)과의 관계

- E3 는 세 항목을 직접 시험하지 않았다.
- 관찰 4(삭제 불가)는 W21 의 설계 경계(scoped backstop 에서 delete 변경은 위반)가 운영에서 드러난 것이다. 화면 소유 파일을 제거하는 작업은 지금 열 수 없다.
- W23·W27 과 직접 겹치는 관찰은 없다.

## 측정 한계

- **회차 간 편차.** 조건마다 1회씩 쟀다. 질문 수·시간·토큰 차이를 편차와 분리할 수 없다.
- **킷 차이.** E2 와 E3 는 킷 절차 문서가 다르다(#263 의 packet 흐름, scoped 문서). 채택의 효과와 문서 차이를 나눌 수 없다. packet 단계 호출은 따로 셌다.
- **사례 1.** scoped 판정을 환경 요인 때문에 관찰하지 못했다.
- **관찰자 보호.** E2 에서 정한 보호 절차(빈 작업 디렉토리 등)를 E3 틀에 넣지 못했다. 대화 기록 스캔으로는 영향을 찾지 못했다.
- **토큰.** 하네스 `subagent_tokens` 는 누적 사용량이 아니라 구간이 끝날 때의 컨텍스트 크기다. 마지막 응답의 입력·캐시·출력 합과 0.3–4.1% 안에서 같았다. 누적 비교는 캐시 읽기 합계로 했다. E3/E2 비는 1.48 · 0.88 · 1.20(첫 구간) · 1.66(재개) · 0.87 이다.
- **범위.** 소비자 1곳의 화면 1개다.
